## 今回の方針: 文字起こしSTT APIのプラガブル対応

### 目的

現在の文字起こしエンジンはGoogle Web Speech / ローカルWhisperの2択のみ。以下のissueが示すように、クラウドの高精度STT API(Groq経由のWhisper large-v3、OpenAIのWhisper API等)やローカルLANサーバー(issue #100)を選べるようにしたいというニーズがある。

- issue #100: ローカル/LAN上のカスタム音声認識サーバーを使いたい(CPU/GPU負荷をVRCT本体から逃がしたい)
- issue #17: Whisperの直接翻訳機能を使いたい
- 他ツールとの比較検討から判明した知見: 体感精度の差は主にVADの精密さではなく**STTモデル自体の質**(クラウドの大規模モデル vs ローカルの小型モデル)に起因する

### アーキテクチャ方針

STT連携でよくある「Protocolベース、非同期・常時ストリーミング前提」の抽象化ではなく、VRCTの既存パイプライン(フレーズ確定後にまとめて1回で送信するバッチ型)に合わせて**同期的なインターフェース**にする。

```
TranscriptionProvider.transcribe(audio_data, language, country) -> (text, confidence)
```

- 既存のGoogle/ローカルWhisperもこのインターフェースに包み直す
- レビューのPhase 3項目17で提案した`TranslationProvider`レジストリと同じ考え方を文字起こし側にも展開する(`transcription_transcriber.py`の`match`分岐を、プロバイダ登録ベースのディスパッチに置き換える)

### 段階分け

STTプロバイダは「バッチ(ファイルアップロード)型」と「リアルタイムストリーミング型」に大別される。VRCTの既存パイプラインはバッチ型なので、まずバッチ型のみ対応し、ストリーミング型は将来アーキテクチャ変更を伴う別フェーズとする。

| フェーズ | 内容 | プロバイダ例 |
|---|---|---|
| **フェーズ1(今回)** | バッチ型REST | OpenAI互換REST(`/v1/audio/transcriptions`、Groq/OpenAI公式/カスタムローカルサーバーを1実装でカバー)→ 次点でDeepgram録音済みREST |
| フェーズ2(将来・別途検討) | リアルタイムストリーミング | OpenAI Realtime Transcription API(WS/WebRTC)、Deepgram WebSocketストリーミング |
| 対象外(必要になれば個別検討) | 専用SDK依存の高コスト対応 | Soniox、Qwen ASR、ローカルSherpa系(Parakeet/Qwen) |

フェーズ1の実装順序: **OpenAI互換REST(Groq/OpenAI/カスタムサーバー)を先に実装・検証・コミット → その後Deepgram録音済みRESTを追加**。

### OpenAI互換RESTプロバイダの実装方針

- 翻訳側の`OpenAICompatibleClient`(`models/translation/translation_openai_compatible.py`)と同様、公式`openai`パッケージ(既存依存)の`client.audio.transcriptions.create(...)`を使う(生の`requests`実装は不要)
- **内部実装(コード)は1つ**(base_urlとモデル名を差し替え可能な共通クラス)で、Groq/OpenAI公式/issue #100のローカルサーバーをカバーする。
- ただし**ユーザーから見えるエンジン選択肢は、翻訳側の`OpenAI_API`/`Groq_API`/`OpenAI_Compatible`が別々の選択肢であるのと同じ構造で、プロバイダごとに分ける**(案B、確定)。各エンジンが専用のキー欄・既定URLを持つため、「今どのキーを使っているか」は選択したエンジン名自体で自明になる。
  - 例: 「Groq Whisper」(既定URL: Groqのエンドポイント、専用キー)、「OpenAI Whisper」(既定URL: OpenAI公式、専用キー)、「カスタムWhisperサーバー」(issue #100向け、URL必須入力、専用キー)
  - `TRANSCRIPTION_AUTH_KEYS`にはこの3エンジン分のキーを用意する

### 名称の整理(確定)

既存のローカル文字起こしエンジン名「Whisper」は**変更しない**(値の変更は`SELECTED_TRANSCRIPTION_ENGINE`に保存済みの既存ユーザー設定のマイグレーションが必要になり、影響範囲が広いため)。新規追加するAPI系エンジンは、プロバイダ名を前面に出した名称にすることで「Whisper」(ローカル)との混同を避ける:

- ローカル(既存、変更なし): `Whisper`
- Groq経由のAPI(新規): `Groq Whisper`
- OpenAI公式API(新規): `OpenAI Whisper`
- カスタムサーバー(新規、issue #100向け): `カスタムWhisperサーバー`(仮称、英語名は実装時に決定)

### APIキー・URL設定の方針(重要な設計判断)

当初「プロバイダ単位でキーを共通化(翻訳と文字起こしで同じGroqキーを共有)」を提案したが、以下の理由により**キーも用途別に分離する**方針に訂正した:

- レート制限/クォータの圧迫: 翻訳と文字起こしが同じキーを共有すると、片方の多用がもう片方のクォータを圧迫する
- 課金/コスト管理を用途別に追跡したいケース
- 認証情報自体が別物であるケース(例: 翻訳は実績のあるクラウドAPI、文字起こしは試験的なローカルサーバー)
- **非対称性**: キーを分けておけば「同じキーを使いたい人」は同じ値を2箇所に入力するだけで済む。逆に統一すると「別々のキーを使いたい人」にはその手段が無くなる。分ける方が安全な既定。

**確定した設計**:
- 既存の`config.AUTH_KEYS`(翻訳用)は変更しない(既存ユーザー設定への影響なし)
- 文字起こし用に新規`config.TRANSCRIPTION_AUTH_KEYS`(同じ形の辞書)を追加する
- エンドポイントURLも用途別に分離する(翻訳用`OPENAI_COMPATIBLE_URL`とは別に、文字起こし用のURL設定を追加)

### UI配置(未確定・データ構造とは独立に決定可能)

APIキー管理UIを以下のいずれにするかは未確定。データ構造(キーを用途別に分離)とは独立して後から決められる:

1. 現状通り、各機能タブ(翻訳/文字起こし)にそれぞれのAPIキー設定を埋め込む
2. 「APIキー」専用の統合タブを新設し、プロバイダ・用途ごとに整理して一覧表示する

「今どのキーを使っているか」は、上記の通りエンジン名自体(Groq Whisper / OpenAI Whisper / カスタムWhisperサーバー)で自明になるため、追加の表示UIは不要。

### 確定した論点

1. **エンジン名の衝突**: 上記「名称の整理」の通り、プロバイダ名を前面に出した名称で解決(確定)。
2. **モデル選択**: 文字起こし側もユーザーがモデルを選択できるようにする(翻訳側の`getModelList()`相当の仕組みを踏襲)。
3. **音声フォーマット**: 各API先の仕様に準拠する(固定フォーマットを決め打ちしない。`AudioData.get_wav_data()`等、実装時にプロバイダごとの要求仕様を確認して対応する)。
4. **エラー種別**: 最低限、以下4種を切り分ける(それ以上は今回追加しない): APIキー無効(認証エラー)/ レート制限 / タイムアウト / サーバーエラー(5xx等その他)。`errors.py`の`ErrorCode`/`ErrorCategory`の枠組みに沿って、この4種に対応する新規エラーコードを追加する。
5. **タイムアウト**: `_HTTP_TIMEOUT`と同じ値((10, 60))をそのまま流用する。実機検証の結果次第で調整する。
6. **クラウド送信の告知**: 追加の告知UIは不要と判断。APIベースのエンジンを明示的に選択する時点で、音声がクラウドに送信されることはユーザーに理解されているとみなす。
7. **テスト方針**: `openai`SDK自体の内部通信は信頼し(SDKのHTTP実装はテスト対象外)、VRCT側のテストは「送信までの処理」(正しいファイル形式・モデル名・パラメータでSDKを呼び出しているか)と「データ取得後の処理」(レスポンスの解釈、エラーハンドリング、transcript状態の更新)の2点に絞る。SDKクライアントをモックして検証する。
