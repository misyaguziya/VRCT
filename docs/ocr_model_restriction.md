# 吹き出し検出モデルを VRCT 専用にする（設計メモ）

「モデル自体は公開するが、VRCT 以外での利用はライセンスで禁止する」構成の設計。
暗号化などの技術的保護は使わず、**配布のしかたとライセンス文面だけ**で組み立てる。

ライセンス文面のドラフトは [`licenses/MODEL-LICENSE.ja.draft.txt`](licenses/MODEL-LICENSE.ja.draft.txt)
（日本語・正文）と [`licenses/MODEL-LICENSE.en.draft.txt`](licenses/MODEL-LICENSE.en.draft.txt)。

## 前提：先に権利を自分のものにする

現在の `chatbox_yolov8n.onnx` は Ultralytics 由来の AGPL-3.0 で、VRCT には制限を
課す資格がない（[`ocr_model_license.md`](ocr_model_license.md)）。下記のどちらかが
済むまで、このメモの内容は発効できない。

- **A. Ultralytics Enterprise License を取得する** — 学習も実装もモデルサイズも
  現状のまま。要年額課金。まず見積もりを取る価値はある。
- **B. Apache-2.0 の基盤で再学習する** — 費用ゼロ。データセットは流用できるが、
  学習スクリプトは書き直し、`ocr_bubble_detector.py` の正規化まわりが変わる。
  候補は YOLOX-Tiny / RTMDet-tiny / D-FINE-N。いずれも ONNX エクスポート時に
  NMS をグラフへ焼き込めば `detect()` 以降は現状のまま使える。

B の副次効果として、`51e60af` 以降 MIT 表記で配布していた期間の汚染も切れる。
A の場合は過去分の扱いが残るので、別途整理が要る。

## 配布設計

### モデルファイルをリポジトリのツリーに置かない

技術的な隠蔽が目的ではなく、**ライセンス上の理由**でこれが必要になる。

GitHub の利用規約 (Terms of Service, D.5 "License Grant to Other Users") は、
パブリックリポジトリを公開した時点で「他のユーザーが閲覧しフォークすることを
許諾したものとみなす」と定めている。つまりリポジトリのツリーにモデルを置いたまま
「再配布禁止」と書いても、GitHub 上でのフォークについては自分で許諾を与えている
状態になり、条項が噛み合わない。

Release アセットはリポジトリのツリーに含まれず、フォークでも複製されない。
BOOTH の配布物も同様。したがって:

| 経路 | 置き場所 | 備考 |
|---|---|---|
| 同梱（配布バイナリ） | `_internal/ocr_onnx/` | 現状と同じ。spec の datas はそのまま |
| ソースから動かす開発者 | Release アセット等から取得 | `tools/fetch_ocr_models.py` と同じ仕組みで足せる |
| リポジトリのツリー | **置かない** | `.gitignore` に追加する |

Release アセットとして置くこと自体は「公開」であり、ユーザーがダウンロードできる
点は変わらない。変わるのは、フォーク権を自動的に与えてしまわないこと。

### ライセンスの提示

同梱する以上、エンドユーザーも被許諾者になる。提示の方法は次のどれか。

1. 配布物に `MODEL-LICENSE.txt` を同梱する（最低限。現状の `LICENSE.txt` /
   `NOTICE.txt` を置き換える形になる）
2. 取得スクリプトがダウンロード前に条文を表示し、明示的な同意を求める
3. VRCT の初回起動時に同意を求める

2 は開発者向けの経路に効き、3 はエンドユーザーに効く。1 だけだと「見ていない」と
言われる余地が残るので、最低でも 1 + 2 は入れたい。3 は UX を悪くするので、
OCR 機能を初めて有効にしたときだけ出す形が落としどころ。

### 取り出しは防げない

配布バイナリの `_internal/ocr_onnx/` にある onnx は誰でもコピーできる。この方針は
それを技術的に防ぐものではなく、「コピーして使ったらライセンス違反になる」状態を
作るもの。実際に止められるのは、法務を通す企業と、依存ライセンスを確認する OSS
プロジェクト。個人の無断流用は止まらない。

そこまで含めて実効性を上げたいなら、再学習のついでに識別情報（特定の合成パターンに
対して特異な出力を返すよう仕込む）を入れておくと、流用の立証と削除要請の根拠になる。
ライセンス文面の第3条(7)はそれを前提にしている。

## 決めておくべき論点

1. **VRCT のフォークを許諾範囲に含めるか。**
   VRCT 本体は MIT なので誰でもフォークして改造できる。ドラフトは許諾対象を
   「VRCT」= misyaguziya が公開するアプリケーションに限定しており、フォークした
   ものは含まれない読み方になる。厳密で抜け道が少ない反面、善意のフォークでも
   吹き出し検出が使えなくなる。緩めると「うちのアプリも VRCT ベースです」という
   抜け道ができる。**どちらを取るかは決め打ちが必要。**
2. **研究・評価目的の例外を置くか。** ベンチマーク比較などを許すなら第2条に
   一項足す。置かないなら何も書かない。
3. **問い合わせ先。** 第6条の個別許諾の窓口。GitHub の Issue でよいか、
   メールアドレスを出すか。

## 制限ライセンスにすると失うもの

- VRCT 本体は MIT の OSS なのに、主要機能の一部が proprietary な部品に依存する
  構成になる。「実質 OSS ではない」という指摘は出る。
- Linux ディストリや一部のパッケージマネージャは扱えなくなる。
- フォークした人がモデルなしでビルドすることになる（論点1の決め方による）。

緩和材料として、`BubbleDetector._ensureSession()` が遅延ロードで、モデルが無くても
VRCT はビルドも起動もでき、OCR の吹き出し検出だけが無効になる設計になっている。
モデルを optional component として位置づけられるので、この批判はかなり和らぐ。
ライセンス文面の第5条はこの事実を明記している。

## 発効させるときの作業

1. A または B を済ませる
2. ドラフトの注記ブロックを削除し、`.draft` を外す
3. `LICENSE` の除外節を AGPL-3.0 から本ライセンスへ差し替える
4. `NOTICE.md` と各言語 README の記述を差し替える
5. `src-python/models/ocr/onnx/` の `LICENSE.txt`（AGPL 全文）を削除し、
   `MODEL-LICENSE.txt` を置く。`NOTICE.txt` も書き直す
6. モデルを `.gitignore` に追加し、ツリーから外す
7. 取得経路（`tools/fetch_ocr_models.py` 相当）と同意表示を実装する
8. `docs/ocr_yolo_training.md` と `src-python/docs/details/ocr.md` の参照を直す

## 注意

このメモとライセンスドラフトは法律の専門家が書いたものではない。発効させる前に
一度弁護士の確認を受けること。特に第3条の禁止事項の書きぶりと、消費者契約法との
関係（エンドユーザー向けの責任制限条項）は素人判断で済ませないほうがよい。
